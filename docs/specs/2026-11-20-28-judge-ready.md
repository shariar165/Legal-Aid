## 3. In-browser Bangla OCR (branch `browser-ocr`)
**Backend.** Reuse the existing OCR path, so the salary confidence check and the OCR card keep working unchanged.
- `/api/health` gets `"ocr": bool`: whether `easyocr` can be imported. Add a cheap `ingestion.ocr_available()`.
- `POST /api/analyze` takes a new form field, `ocr_lines`: a JSON list of `{text, conf}` with conf in [0,1], at most 400 lines and 60k characters. It is sent with the original filename and no file.
  - `ingestion.build_document` gets an `ocr_lines` argument, which builds `Extracted(kind="image", ocr_lines=…)` directly.
  - `ocr_used`, `ocr_confidence` and `salary_confidence` (`ingestion.py:429-439`) work as before.
  - Validation: a field that is not JSON or out of bounds gives a 400.
- PII: the text then goes through `pii.py` like any upload. No new outbound path.
- `orchestrator.py:116-119`: an `OcrUnavailable` error shows its own message, without the `OcrUnavailable:` prefix. A scanned PDF on lite still gets that clear refusal; browser OCR of PDFs is out of scope.
- Tests in `tests/test_api.py` and `tests/test_ingestion.py`:
  - `ocr_lines` with a low-confidence salary line pauses for the salary check,
  - bad JSON, too many lines and conf > 1 each give a 400,
  - health reports `ocr`,
  - the OcrUnavailable message comes through clean.

**Web.**
- Add `tesseract.js` (Apache-2.0). Its worker, core wasm and `tessdata_fast` `ben` + `eng` traineddata are self-hosted under `web/public/ocr/`, so no third-party CDN sees the visit.
- `web/src/lib/citizen/browserOcr.ts`:
  - load the library on first use with a dynamic `import()`,
  - downscale the image to 2200px like the server does,
  - recognise with `ben+eng`,
  - map tesseract lines to `{text, conf: confidence/100}`, using the minimum word confidence per line to match `ingestion.py:94`,
  - report progress.
- `useAnalysis.start` / `api.ts`: read `health.ocr` once.
  - When it is false and the file is an image, OCR it in the browser, then send `ocr_lines` instead of the file.
  - The AnalyzingScreen shows a first step "ফোনেই ছবি পড়া হচ্ছে / Reading the photo on your phone" with its progress.
  - A HEIC photo, or an OCR that reads nothing, gets a clear message.
- i18n strings go in `i18n.ts`.
- **Confidence calibration.** Tesseract's minimum word confidence usually comes out lower than EasyOCR's, so the same `OCR_CONFIDENCE_FLOOR` (0.9) could raise the salary check on almost every photo.
  - Run the browser path on the demo photo and on 2–3 new photos (fictional contracts, no real company). For each, record the salary line's confidence, whether the salary check appears, and whether the amount was read correctly.
  - If the check appears on correctly read salaries, give the browser path its own floor. Send `ocr_engine: "tesseract"` with the lines, and add `ocr.browser_confidence_floor` in `config.yaml`, set from the recorded numbers. Add a test that each engine uses its own floor.
  - If `tessdata_fast` `ben` reads Bangla badly (the salary or key clauses come out wrong), try `tessdata_best` `ben`, and record both its size and its accuracy.
- **Gate 3:** run fake mode with the backend's OCR forced off, upload the demo photo through the file input, and check that the OCR card and the result appear. Time it on desktop Chrome and record the time.

  step left to try: Bangla text came back at 93–96% on readable photos.

**Calibration** (`web/scripts/ocr-calibrate.mjs`, same engine, models and line rule as the browser; fictional
contracts rendered as phone photos the way `make_photo_sample.py` does: the demo photo, the Saudi and EPZ
contracts, a new all-Bangla contract, then blur 1.4/1.6/1.8 and 2.2–2.6 variants). Salary confidence = the
salary line's weakest word, as the backend computes it.

| Photo | Text read | Salary found | Correct? | Salary conf |
|---|---|---|---|---|
| demo (MY) | 99% | RM 1,200 | yes | 0.94 (EasyOCR: 0.768) |
| SA phone | 99% | SAR 1,000 | yes | 0.90 |
| EPZ rough | 100% | BDT 12,500 | yes | 0.91 |
| BN phone / clean | 96% | RM ১,৫০০ | yes | 0.53 / 0.72 |
| SA blur 1.4 / 1.6 | 99 / 97% | SAR 1,000 | yes | 0.92 / 0.19 |
| MY blur 1.8 | 97% | RM 1,200 | yes | 0.29 |
| MY blur 1.4 / 1.6 | 99 / 98% | RM 1.2 ("1.200") | **no** | 0.61 / 0.38 |
| BN blur 1.4 / 1.8 | 93 / 86% | RM 300 (deduction line) | **no** | 0.68 / 0.15 |
| BN blur 1.6 | 93% | RM ১.৫ | **no** | 0.42 |
| SA blur 1.8 | 96% | SAR 1 (wrong line) | **no** | 0.53 |
| three at blur 2.2–2.6 | 59–84% | none | – | mean line conf 0.06–0.22 |

- Tesseract is *confidently wrong* on digits: "1.200" for "1,200" scored 91–93 on the digit word, so a
  digit-only confidence is no signal. The line's weakest word is: every wrong read was 0.68 or less.
- **Floor for tesseract stays 0.9** (`ocr.confirm_floor.tesseract`): it asks on 6/6 wrong reads and on 4/9
  correct ones (Bangla lines score low even when right, so a Bangla photo almost always gets the one-tap check).
  A lower floor would let 0.61–0.68 misreads through. The per-engine key stays, so EasyOCR and tesseract can move
  apart if live photos show a need. English photos score *higher* on tesseract than EasyOCR (0.94 vs 0.768 on the
  demo photo), the opposite of the expected direction.
- **New: a blurry gate on the device.** A photo whose mean line confidence is under 0.25 is sent back to be
  retaken (`ocr_blurry`), and nothing is sent: those photos never yielded a salary. The lowest readable test
  photo scored 0.29.
- Timing (desktop Chrome, headless): 4.5–5.1 s to the salary check or result for a one-page photo, 12 s to the
  blurry message; a phone will be slower. Gate 3 at 390px: `docs/design/ocr-device-progress.png`,
  `ocr-device-salary-check.png`, `ocr-device-blurry.png`. The request carried `ocr_lines` and `ocr_name` only,
  no file.
- An EasyOCR run on the Bangla photos for a side-by-side was killed by low memory; the demo photo is the one
  paired number.

## 5. Voice check (branch `voice-check`)
`web/src/lib/citizen/useSpeech.ts`:
- Pick a voice whose `lang` starts with the wanted language: `bn` first, and any `bn-*` counts. Use `getVoices()` and `voiceschanged`.
- Split long text into sentence chunks on `।`, `.`, `?`, `!` and newlines, about 200 characters each, then speak them one after another. This avoids Chrome's cut-off after about 15 s.
- Progress follows the chunks instead of the 75 ms/char guess.
- Add `onerror`, and cancel when the page is hidden.
- **No Bangla voice:** don't fake progress. Return `unavailable`, and have `ResultScreen`/`HomeScreen` show one honest line, "এই ফোনে বাংলা কণ্ঠ নেই / No Bangla voice on this device", instead of a silent progress bar.
- **Check:** on desktop Chrome (usually no bn voice) the honest line shows. On Edge or Android with a bn voice, the letter is read to the end.
