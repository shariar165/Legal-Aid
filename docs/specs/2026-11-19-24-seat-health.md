# Seat health: a rejected key (seat-health)

Branch `seat-health` off main after PR #3. Asked for directly after production was found running a revoked OpenRouter
key while `/api/health` showed every seat on its configured model: a 401 counted as "unknown", which never moves a seat.

## Change
- `llm.py`: a 401 or 403 raises `_KeyRejected` ("<provider> key rejected (401)"), never quoting the provider's reply.
  Every route failure carries a short `reason`; the answer that falls back records it as
  `OutboundCall.fallback_reason` (first failed route on this call, else the seat check's reason for its pick).
- `seat_health.py`: `SeatHealth.status` (ok / gone / key_rejected / unknown) and `key_rejected` (providers). A rejected
  key moves the seat like a gone model, but nothing is marked gone; one refusal answers for the provider's other models
  (no extra pings). Only "ok" and "gone" pings are kept across restarts, so a replaced key is pinged at the next start.
- `BenchOpinion.fallback_reason`; the Council shows "key rejected, fell back to <model>". The trace chip names the
  reason. `/docs` gets a seat table and says "key rejected" next to the provider instead of "key set".

## Verification
- `pytest` offline: 358 passed. New tests (fake 401 and 403 from the MockTransport, a reply that echoes a secret):
  seat marked key_rejected and moved to its Groq backup, no OpenRouter fallback model pinged, `/api/health` status,
  the call's `fallback_reason`, nothing from the reply in logs, errors or health, a replaced key seen after a restart,
  the opinion carries the reason.
- Browser (fake mode, `fetch` stubbed with the dead-key seats): /docs seat table and Model mode tile, Council ruling.
